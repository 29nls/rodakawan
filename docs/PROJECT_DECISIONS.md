## Keputusan Milestone 1.6 lanjutan (tag versi dibuat workflow)

| ID | Keputusan | Status | Alasan / catatan |
|---|---|---|---|
| ADR-042 | Rilis produksi dijalankan **manual** lewat `workflow_dispatch` dengan input `version` (bukan push tag `v*` seperti ADR-038), dan tag `v<versi>` dibuat job `release` **setelah** build EAS sukses dan APK-nya lolos verifikasi — satu perintah `gh release create --target`, tanpa langkah `git tag` + `git push` dan tanpa `--verify-tag` | Disetujui | Pada alur lama tag versi didorong manusia lebih dulu sebagai pemicu, sehingga build yang gagal meninggalkan tag tanpa release dan tanpa APK — keadaan yang justru ingin dihindari pada rilis produksi. `gh release create` membuat tag yang belum ada dari commit `--target`, jadi tag dan release lahir dari perintah yang sama dan tidak ada langkah di antara keduanya yang bisa gagal separuh jalan; `--verify-tag` dihapus justru karena flag itu membatalkan pembuatan tag. Yang berubah dari ADR-038 hanya pemicu dan siapa yang membuat tag: pemisahan izin (job `EXPO_TOKEN` tanpa izin tulis, job `contents: write` tanpa secret Expo) dan verifikasi berkas APK tetap dipertahankan. Job `verify` menerima input `version` sebagai niat manusia, menolaknya bila tidak sama dengan `expo.version` di `app.json` (label rilis harus sama dengan versi di dalam APK), dan menolak versi yang tag-nya sudah ada — fail-closed, tag lama tidak pernah ditimpa, sehingga tidak ada rilis yang menempel pada tag dari commit lain. `concurrency: android-release` menahan dua rilis agar tidak berlomba memperebutkan versi/tag yang sama. Karena tag tidak lagi menjadi pemicu, pengecualian pola `!v*-build*` dihapus dari `on.push.tags` dan kontrak penamaan tag build preview tidak lagi diperlukan — tag build preview tidak mungkin memicu rilis produksi. Konsekuensi: `workflow_dispatch` tidak lagi menghasilkan artifact tanpa rilis, karena dispatch sekarang selalu berujung rilis bila build sukses; build produksi tanpa rilis dilakukan lokal (`npx eas-cli@latest build --profile production-apk`, SETUP_GUIDE 6.1/6.4). |

## Keputusan Milestone 1.6 lanjutan (APK harus benar-benar tertandatangan)

| ID | Keputusan | Status | Alasan / catatan |

| ADR-043 | Sebelum APK diunggah sebagai Actions artifact dan dilampirkan ke GitHub Release, berkasnya diverifikasi `scripts/verify-apk.mjs`: struktur ZIP (EOCD berakhir tepat di akhir berkas, CRC-32 tiap entri), tanda tangan APK v2/v3 (digest konten chunk 1 MiB + tanda tangan atas `signedData` dengan sertifikat yang tertanam), dan rantai tanda tangan v1 (entri → `MANIFEST.MF` → `.SF` → PKCS#7). Gate ini menggantikan pemeriksaan header `PK` di ADR-038 dan berlaku di `android-release.yml` maupun `release-on-push.yml` | Disetujui | Pemeriksaan lama hanya membuktikan berkasnya arsip ZIP: APK tanpa tanda tangan (Android menolak memasangnya), APK yang isinya diubah setelah ditandatangani, dan arsip yang terpotong semuanya lolos, lalu ikut terunggah ke halaman Releases. Verifikasi tanda tangan adalah satu-satunya cara memastikan berkas itu benar-benar keluaran build ini dan bukan hasil modifikasi. Implementasinya ditulis di Node tanpa `apksigner`/Java supaya gate rilis tidak bergantung pada isi image runner (`apksigner` memang ada di runner GitHub, tapi versinya ikut berubah kapan saja); sebagai gantinya pemeriksaan ini diuji langsung terhadap `apksig` — library resmi yang dipakai AGP/EAS untuk menandatangani — pada APK contoh yang ditandatangani v1/v2/v3 (RSA dan EC), APK nyata F-Droid 113 MB, APK hasil `jarsigner`, serta sepuluh variasi berkas rusak/tanpa tanda tangan. Aturan penilaian mengikuti `apksigner`: minimal satu skema harus terverifikasi dan tidak boleh ada skema yang hadir dalam keadaan tidak valid. Job `release` tetap **tidak** menjalankan kode repository (tanpa checkout) karena memegang `contents: write`; jaminan tanda tangan berlaku di sana lewat pemeriksaan `sha256sum --check` yang membuktikan berkasnya identik dengan berkas yang sudah diverifikasi. Konsekuensi: APK yang gagal diverifikasi menggagalkan workflow sebelum tag dibuat, dan sidik jari sertifikat penandatangan dicatat di ringkasan run agar setiap versi bisa ditelusuri ke sertifikatnya. |

| ADR-051 | Kedua workflow rilis membangun APK sendiri di runner GitHub — `npx expo prebuild --platform android` lalu `./gradlew :app:assembleRelease` — menggantikan `eas build`; keystore rilis disimpan sebagai secret repository dan ditulis ke runner hanya tepat sebelum dipakai, `EXPO_PUBLIC_*` dibaca dari *variables* repository lewat `scripts/write-app-env.mjs`, dan `versionCode` dihitung dari riwayat repository (jumlah seluruh commit) dengan `android.versionCode` di `app.json` sebagai lantai | Disetujui | Alasan utamanya kuota, bukan kecepatan: EAS Build Free membatasi jumlah build per bulan, dan setelah kuotanya habis build **diblokir** sampai bulan berikutnya — bukan sekadar menunggu lebih lama di antrean. Jalur preview membuat satu build untuk **setiap push ke `main`** yang mengubah isi aplikasi, jadi batas itu adalah langit-langit alur rilisnya sendiri: setelah sekian push, satu-satunya pilihan adalah menunggu atau menambah biaya. Membangun di runner menghapus ketergantungan pada layanan pihak ketiga untuk *artefaknya*; untuk repository publik menit runner GitHub tidak berbayar, dan untuk repository privat biayanya mengikuti kuota Actions akun yang sudah ada. Yang dikorbankan: halaman build EAS beserta lognya (digantikan halaman run Actions dan ringkasan yang sudah ditulis tiap job), pengelolaan versi remote milik EAS (digantikan hitungan dari riwayat repository), dan penyimpanan keystore di sisi EAS (digantikan secret repository). Keuntungan lain yang tidak direncanakan tetapi mengikuti: rantai build kini bisa dijalankan **di laptop dengan perintah yang sama** dan tanpa akun apa pun, dan APK yang diverifikasi `scripts/verify-apk.mjs` adalah berkas yang kita hasilkan sendiri, bukan berkas yang diunduh dari layanan lain. Risiko yang diterima karena kunci penandatangan kini berada di CI: kunci itu hanya ditulis ke runner **setelah** `npm ci` dan `expo prebuild` (dua langkah yang menjalankan kode pihak ketiga) selesai, ditulis ke `RUNNER_TEMP` di luar workspace supaya tidak mungkin ikut menjadi isi artifact, berizin `600`, dihapus lagi pada langkah `if: always()` di akhir job, dan job itu tidak punya izin tulis repository. Toolchain-nya tidak dibiarkan mengikuti bawaan runner: JDK 17 dipilih eksplisit (versi minimum yang didukung AGP), image dipin ke `ubuntu-24.04`, dan NDK yang dipin proyek (27.1.12297006 dari template RN 0.86, sedangkan image menyediakan versi lain) diunduh Gradle sendiri setelah lisensi SDK diterima di langkah pertama job — perilaku itu dibuktikan dengan menjalankannya. Nomor `versionCode` tidak lagi bisa datang dari EAS: ia harus urut menaik pada **satu** urutan untuk dua workflow, karena APK preview dan APK produksi memakai id paket dan kunci yang sama, sedangkan `github.run_number` hanya unik per workflow. Jumlah seluruh commit (`git rev-list --count --all`) dipilih karena tidak pernah turun selama repository bertambah commit, dari commit mana pun build dijalankan — termasuk dispatch manual dari branch yang belum di-merge (ADR-044), yang bisa punya hitungan lebih besar daripada `main`. Konsekuensinya nomor itu milik *repository saat build dijalankan*, bukan milik commit: membangun ulang commit lama setelah ada commit baru menghasilkan nomor lebih besar, dan itu diterima karena yang penting hanya APK berikutnya tidak pernah bernomor lebih kecil daripada yang sudah terpasang; `android.versionCode` di `app.json` menjadi lantai yang bisa dinaikkan manusia bila riwayat repository pernah di-rewrite. Ketentuan versi di ADR-036 karena itu diperbarui: `cli.appVersionSource` di `eas.json` kembali ke `local`, supaya build EAS manual (development client, AAB ke Play) memakai angka dari `app.json`, bukan penghitung remote yang tidak lagi dilihat CI. Alur rilisnya sendiri **tidak berubah**: job, keluaran (`apk_name`, `apk_sha256`, `apk_signer_sha256`, `app_version`), nama artifact, uji nyala di emulator, tag, catatan rilis, pencatatan changelog, dan pemangkasan rilis preview semuanya tetap sama — yang berganti hanya siapa yang menghasilkan berkasnya. Batas yang diketahui: tidak ada lagi log build pihak ketiga maupun riwayat build terpusat (yang ada halaman run Actions), waktu build di runner kurang lebih belasan sampai dua puluhan menit dan tidak lebih pendek daripada cloud build yang dulu dipakai, keystore yang hilang atau diganti membuat instalasi lama tidak bisa diperbarui lagi, build EAS manual tidak bisa dipasang berdampingan bila keystore rilisnya bukan keystore yang sama, dan sampai ADR ini ditulis rantai barunya baru dibuktikan **di mesin pengembang** (prebuild, tanda tangan, `assembleRelease`, `verify-apk`), belum pernah berjalan di GitHub Actions. |
